# Tabular Forensics: Detecting Programmatic Generation in Spreadsheet Files

## Problem Statement

Excel files (.xlsx) can be generated programmatically or by hand. When working with shared workbooks, macro notebooks, or automated pipelines, it's useful to detect whether a file was:

1. **Hand-edited** — user opened Excel, typed values, saved
2. **Programmatically generated** — script (Python/openpyxl, C#/EPPlus, Java/Apache POI) created the file
3. **Automated via macros** — VBA macros ran and modified data

This matters for:
- **git-sheets**: tracking whether changes are from automation or human edits
- **Data provenance**: knowing if values were calculated or manually entered
- **Change detection**: distinguishing structural changes from content changes

## Technical Background

### .xlsx Internal Structure

An .xlsx file is a ZIP archive containing XML files:

```
[xl/workbook.xml]          # workbook-level settings, sheet references
[xl/worksheets/sheet1.xml] # cell data, formulas, styles
[xl/sharedStrings.xml]     # shared string table (deduplicated text)
[xl/styles.xml]            # cell formatting definitions
[xl/definedNames.xml]      # named ranges and formulas
[xl/connections.xml]        # external data connections
[xl/customProps.xml]       # custom document properties
```

### Traces of Programmatic Generation

Different generation methods leave distinct signatures:

**Hand-edited files typically have:**
- Irregular cell formatting (inconsistent styles)
- Manual formula entry patterns
- No or minimal shared strings optimization
- User-defined named ranges only for specific purposes

**Programmatically generated files often show:**
- Uniform formatting across all cells (generated by default styles)
- Systematic shared string table usage
- Defined names following programmatic patterns (e.g., `Sheet1.Range("A1")`)
- Custom properties set by the generating library (e.g., `Application: Microsoft Excel` vs `Application: openpyxl`)
- Connection strings pointing to data sources

**Macro-generated changes show:**
- VBA project files (`xl/vbaProject.bin`)
- Defined names for automation purposes
- External links to other workbooks

## Implementation Plan

### Phase 1: Basic Inspector Tool

Build a CLI tool that inspects .xlsx files and reports:

```bash
tabular-inspect file.xlsx
# Output:
# File type: xlsx
# Sheets: 3 (Sheet1, Sheet2, Sheet3)
# Shared strings: 45 entries
# Defined names: 2 (Range1, Total)
# Custom properties: Application=Microsoft Excel
# External connections: none
# Macros present: no
```

**Implementation:** Rust program using `zip` crate to extract and parse XML files.

### Phase 2: Pattern Detection

Analyze file characteristics to classify generation method:

- **Format consistency score**: How uniform are cell styles?
- **Shared string density**: Ratio of shared strings to total cells
- **Formula patterns**: Are formulas manually entered or generated?
- **Metadata analysis**: Check creation/modification timestamps, application info

### Phase 3: Change Detection (git-sheets integration)

Compare two versions of a spreadsheet and report:

- Structural changes (new sheets, columns added/removed)
- Content changes (cell values modified)
- Formatting changes
- Formula changes
- Named range changes

## Key Design Decisions

1. **Language**: Rust (consistent with pesti-structural-tokenizer approach)
2. **Dependencies**: `zip` for archive handling, `quick-xml` or `serde_xml` for parsing
3. **Architecture**: Single-pass inspection — open file, read all relevant XML, report findings
4. **Output format**: Structured JSON for programmatic use, human-readable text by default

## Success Criteria

The tool can reliably distinguish between:
1. Hand-edited Excel files
2. Files generated by common libraries (openpyxl, EPPlus, Apache POI)
3. Files modified by VBA macros

With at least 80% accuracy on a test set of known examples.
